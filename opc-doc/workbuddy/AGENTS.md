# OPC 小红书运营项目规则

本项目用于从 0 到 1 运营 Evan 的小红书 OPC 账号。OPC 暂按 `One Person Company / 一人公司实践` 理解：以 Evan 的真实工作经验、AI 实践和个人系统建设为素材，服务普通职场人从迷茫、焦虑到可执行行动的转化。

任何 agent 在本项目工作时，优先遵守本文件；同时按任务阶段调用 `knowledge-base-operator`、`xiaohongshu-ops`、`cheat-on-content` 三个 skill。不要把它们混成一个万能助手：先读定位，再做平台运营，再做预测校准。

## 1. 项目目标

- 建立一个可持续的小红书内容运营系统，不做一次性灵感输出。
- 账号主线是 `懂产品、懂项目、懂职场`，AI 是杠杆，不是唯一人设。
- 近期商业假设是 `内容 IP + 虚拟资料`，先验证内容吸引力和资料需求，不默认走重交付、重销售、频繁露面路线。
- 每次工作都要留下可复用资产：选题、标题、结构、封面思路、发布记录、评论信号或复盘结论。

## 2. 目标用户

默认面向以下人群写内容：

- 初入职场或工作 1-5 年、方向感不足的人。
- 想转岗、找工作、提升职场基本功的人。
- 对 AI 有焦虑但不知道从哪里开始的普通打工人。
- 像过去的 Evan 一样，知道要成长，但缺一套可执行方法的人。

不要把内容写给已经高度成熟的创业者、资深 AI 玩家或纯技术开发者，除非用户明确要求。

## 3. 内容定位

内容应围绕 5 条主线展开：

- `AI 焦虑`：把焦虑翻译成一个今天能做的小动作。
- `AI 最小实践`：用低门槛场景展示 AI 怎么帮普通人省时间、提质量。
- `职场提效`：产品、项目、沟通、协作、汇报、复盘的具体方法。
- `副业探索`：从内容、资料、自动化、小产品开始，不鼓吹暴富。
- `个人系统 / 一人公司`：知识库、工作流、复盘机制、长期资产建设。

这些是待验证假设，不是已经被数据证明的结论。发布后必须用真实互动数据校准。

## 4. 账号语气

默认语气：接地气、朴实、真实、专业，带一点轻微吐槽感。

写作时遵守：

- 说人话，短句优先，避免报告腔。
- 观点要清楚，但不要端着。
- 先给结论，再给理由或例子。
- 不制造“月入十万”“普通人逆袭”这类空泛承诺。
- 不写 AI 味重的排比、宏大叙事、过度包装话术。
- 能用真实工作场景解释，就不要用抽象概念解释。

小红书评论、私信、发布执行相关文案还要读取并遵守 `xiaohongshu-ops/persona.md`。

## 5. Skill 分工

本项目的默认运营链路由三个 skill 组成：

1. `knowledge-base-operator`：读取 Evan 的知识库定位，确认账号长期方向和个人经验素材。
2. `xiaohongshu-ops`：负责小红书账号分析、选题、对标、内容结构、发布前演练、发布记录和发布后复盘。
3. `cheat-on-content`：负责发布前预测、发布后校准、rubric 进化，以及判断某条内容是否值得衍生虚拟资料。

### 5.1 knowledge-base-operator 的职责

涉及账号定位、个人经历、内容 IP、知识库素材、项目长期方向时，先调用 `knowledge-base-operator`。

默认读取和参考：

- Evan 的知识库定位和个人说明。
- 已沉淀的项目、技能、资源、输出和复盘。
- 与 `懂产品、懂项目、懂职场` 相关的真实经历和可复用方法。

输出要求：

- 给出当前任务可用的定位摘要。
- 指出能复用的个人素材、方法或观点。
- 把新结论沉淀回知识库或本项目 `knowledge-base/`。
- 不把知识库整理成泛泛总结，要回答“下一步能拿来做什么”。

### 5.2 xiaohongshu-ops 的职责

凡涉及小红书平台、账号、选题、对标、发布、评论、复盘，必须调用 `xiaohongshu-ops`。

典型任务：

- 账号定位和账号体检。
- 首页推荐流、搜索结果、竞品账号和爆款笔记分析。
- 选题池、标题、封面文案、正文结构、互动问题和话题生成。
- Viral Copy：学习爆款结构，但不照抄。
- 发布前演练和发布页填写。
- 发布后评论信号、互动结构和内容表现复盘。

平台操作必须使用 OpenClaw 内置浏览器 profile `openclaw`。涉及发布时，默认到 `发布` 按钮可见处停手，除非用户明确授权点击发布。

### 5.3 cheat-on-content 的职责

凡涉及“这篇值不值得发”“哪条选题优先”“发前预测”“发后校准”“是否做虚拟资料”，必须调用 `cheat-on-content`。

首次使用前必须先初始化 `cheat-on-content`，确保项目内存在它需要的状态文件、rubric、候选池、预测日志和工作流文件。

默认使用方式：

- 发布前：对最终稿或候选选题做评分与盲预测，形成 immutable 预测记录。
- 发布登记：发布后记录链接、平台 ID、发布时间和内容状态。
- 发布后：按 T+3d 或用户提供的数据做复盘，校准 rubric。
- 资料判断：根据收藏、评论问题、私信需求、主页访问和内容主题，判断是否进入虚拟资料候选池。

必须遵守：

- 预测必须在看到实际数据前完成。
- 预测记录写入后不可改 `## 预测` 段，只能追加复盘。
- 没有真实数据时，只能做 cold-start 判断，不制造精确数字。
- 不凭感觉推荐选题，必须展示评分维度和判断理由。

## 6. 默认工作流

开始任何任务前：

1. 判断任务类型：定位、选题、对标、内容稿、封面/配图、发布、评论、复盘、虚拟资料。
2. 先用 `knowledge-base-operator` 读取知识库定位和可复用素材。
3. 再读取本项目 `knowledge-base/README.md`，检索最近 7-14 天同类记录。
4. 需要小红书账号、选题、对标、发布或复盘时，用 `xiaohongshu-ops`。
5. 需要发布前判断、发布后校准或资料候选判断时，用 `cheat-on-content`。
6. 最多问用户 3 个具体问题；能从现有上下文合理判断的，不要反复追问。

执行任务时：

1. 优先产出可执行结果，而不是泛泛建议。
2. 选题默认给 3-5 个，每个包含标题方向、开头钩子、正文结构、互动问题、风险点。
3. 内容稿默认至少给 2 个备选标题。
4. 发布前先用 `cheat-on-content` 做评分和盲预测；未预测的稿子默认不进入正式发布。
5. 发布任务默认走到发布按钮可见处停手，除非用户明确授权点击发布。
6. 评论回复默认 `one-send-per-turn`，不连续批量发送，避免风控和语气失控。

结束任务时：

1. 把结果沉淀到 `knowledge-base/` 对应目录。
2. 明确记录本次结论、证据、可复用点、风险、下一步。
3. 如果发生发布动作，同步登记到 `cheat-on-content` 的预测/发布/复盘链路。
4. 如果没有真实数据，只能标记为 `experimental` 或 `hypothesis`，不能写成验证结论。

## 7. 知识库规则

固定入口：

- `knowledge-base/README.md`

固定目录：

- `knowledge-base/accounts/`：账号定位、账号体检、竞品账号分析。
- `knowledge-base/topics/`：选题、争议点、标题骨架、内容方向。
- `knowledge-base/patterns/`：爆款结构、封面层级、互动机制、可复用 pattern。
- `knowledge-base/actions/`：发布、回复、搜索、抓取、复刻等动作记录。
- `knowledge-base/reviews/`：结果复盘、失败原因、下次调整。

记录文件命名：

```text
YYYY-MM-DD-brief.md
```

每条记录至少包含：

- 一句话结论
- 证据或来源
- 可复用点
- 风险或边界
- 下一步动作

知识库只存可复用信息，不堆流水账。

## 8. 小红书平台操作规则

凡涉及小红书浏览、搜索、发帖、评论：

- 必须使用 `xiaohongshu-ops` skill。
- 默认只使用 OpenClaw 内置浏览器 profile `openclaw`。
- 搜索内容时只从搜索结果页进入帖子，不直接跳 `/explore/<id>`。
- 关键节点保留少量快照：登录确认、进入帖子、发布页、填写完成、发布前停顿。
- 单步动作最多重试一次；失败后改稳健路径并说明当前卡点。
- 不盲目批量评论、批量私信或频繁操作。
- 涉及发布，除非用户明确授权，否则到 `发布` 按钮可见处停手。

## 9. 内容生产格式

默认小红书图文输出结构：

```markdown
## 版本 A

标题：
封面文案：
开头钩子：
正文：
互动提问：
话题：
风险：

## 版本 B

标题：
封面文案：
开头钩子：
正文：
互动提问：
话题：
风险：
```

正文优先采用三段式：

1. 观点：先说一句清楚判断。
2. 场景：用真实工作/学习/副业场景说明。
3. 行动：给一个今天能做的小动作。

## 10. 复盘规则

发布后复盘默认看：

- 曝光、点赞、收藏、评论、关注、主页访问。
- 标题是否带来点击。
- 封面是否能 1 秒说清利益点。
- 正文是否引发评论或收藏。
- 评论区真实问题是什么。
- 是否出现可复用标题、钩子、结构或资料产品线索。

复盘输出默认包含：

- 最大有效点
- 最大短板
- 下一篇怎么改
- 是否值得沉淀为 pattern
- 是否衍生虚拟资料选题
- `cheat-on-content` 的预测是否命中，rubric 是否需要调整

## 11. 虚拟资料候选判断

内容不直接等于资料产品。只有出现明确需求信号时，才进入虚拟资料候选池。

候选信号：

- 收藏明显高于点赞，说明用户想回看。
- 评论里出现“模板”“清单”“怎么做”“能不能发一份”。
- 私信或主页访问有增长。
- 同一主题连续 2-3 篇都有反馈。
- 内容能沉淀成表格、清单、SOP、提示词、案例库或训练营前置资料。

判断流程：

1. `xiaohongshu-ops` 收集发布后互动、评论和内容结构信号。
2. `cheat-on-content` 对表现和预测偏差做复盘，判断资料候选价值。
3. `knowledge-base-operator` 把可复用方法沉淀到知识库，并决定属于 Skill、Resource、Output 还是 Review。

输出默认包含：

- 是否进入资料候选池
- 候选资料名称
- 用户真实需求证据
- 最小可交付形态
- 下一次内容如何继续验证

## 12. 边界

- 不制造虚假经历、虚假收入、虚假案例。
- 不输出无法验证的数据结论。
- 不为了流量夸大焦虑或制造羞辱感。
- 不直接照抄爆款笔记；只能学习结构、节奏、封面信息层级和互动机制。
- 不删除知识库历史记录；失效内容标记为 `deprecated`。
- 不绕过 `cheat-on-content` 的盲预测，把已知结果倒推成“预测”。
- 不把单条内容的偶然数据直接包装成确定的商业结论。

## 13. 当前 0-1 路线

第一阶段目标不是涨粉最大化，而是找到 `人群-问题-表达方式-可转化资料` 的最小闭环。

建议按 4 周运行：

- 第 1 周：账号定位、竞品分析、10 条选题池、3 条试发内容。
- 第 2 周：围绕 AI 焦虑和职场提效各发 2-3 条，观察收藏和评论问题。
- 第 3 周：把有效主题扩成系列，开始设计 1 个轻量虚拟资料。
- 第 4 周：复盘数据，保留 2-3 个稳定栏目，淘汰无反馈方向。

每周结束必须写一条 `knowledge-base/reviews/` 复盘。

每条正式发布内容都尽量经过以下闭环：

```text
knowledge-base-operator 读取定位和素材
-> xiaohongshu-ops 生成选题/对标/内容/发布复盘
-> cheat-on-content 发布前预测
-> xiaohongshu-ops 发布后收集平台信号
-> cheat-on-content 发布后校准和资料候选判断
-> knowledge-base-operator 沉淀方法、输出和复盘
```
